### FIX-5: 探索開始位置を「内部ランク j」から「未割当プレイヤー中の順位 r」へ

各フェーズの探索サブフェーズ開始時に、未割当プレイヤー（`f[m] == -1`）の内部ランク
集合を昇順に並べ、自身が何番目か（r ∈ {1, .., M'}, 1-based）を計算して開始位置とする。
r は未割当プレイヤー間で相異なり r <= M' <= |K| なので、開始位置の mod 衝突は起きない。

**index 規約に関する注意（指示からの意図的な乖離）**:
指示では「最初に引くアームが active_arms の (r-1) % Ka 番目になるように」とあったが、
現実装（および変更禁止の huang2022 実装）は pre-increment 規約
「初期値 pos = (j-1) % Ka → 最初に引くのは active_arms[j % Ka]」を採っている。
文字通り (r-1) % Ka 番目を最初に引くようにすると、r == j の場合（n=1 の全域を含む）でも
全行動列が 1 ステップ分回転し、
「主実験のビット単位一致（検証 2）」と「n=1 と huang2022 の軌跡等価（検証 3）」が
**両方とも必ず破綻する**。そこで本実装は「j を r に置き換えるだけ」
（初期値 pos = (r-1) % Ka → 最初に引くのは active_arms[r % Ka]）とした。
これは論文 Algorithm 5 のホッピング列を全員一様に +1 回転したものであり、
FIX-5 の本質（未割当プレイヤー間で開始位置が相異なること）は保たれる。
r == j の間は従来実装・huang2022 と行動列が完全に一致する。

### FIX-4(a): チャネル棄却済みサブリーダーの救済

フェーズを跨いで `C_reject` を蓄積した累積棄却集合 `rejected_cum` を保持し、
n>1 の割当パスで「未割当のフォロワー（j > n）と、担当チャネル `good_arms[j-1]` が
`rejected_cum` に入っている未割当サブリーダー（j <= n）」を内部ランク降順に並べ、
`C_assign_list`（accept 腕から good arms を除いた列）の先頭から 1 対 1 で割り当てる。
割当の一括計算（相開始時の M0 を固定し、M0 更新は割当確定後に一度だけ）と
n=1 の分岐（Huang 2022 相当）は従来のまま。

### 検証用カウンタ（`run()` 後にインスタンス属性として読める）

- `hde_fix5_r_neq_j_count`: r != j となった (フェーズ, プレイヤー) の延べ回数
- `hde_fix4a_rescue_count`: 救済パスで割り当てられたサブリーダーの延べ人数
- `hde_channel_rejected_count`: 救済の前提条件（担当チャネルが累積棄却集合に入った
  未割当サブリーダー）が観測された延べ回数

## 2. 検証結果

環境: Python 3.12.1（pandas 2.3.1）。再実行はすべて保存済み `run_config.json` の設定
（seed_base=20260510、trial ごとの seed・retry 設定を含む）を忠実に再現する
ドライバで行い、trial 単位の並列化のみを行った（trial 間は独立なので結果は逐次実行と同一）。

### 検証 1: テストスイート ✅

`pytest tests/` 80 件すべて成功（修正後・カウンタ追加後の両時点で確認）。

### 検証 3: n=1 と huang2022 の軌跡等価 ✅

主実験設定の seed 20260510〜20260512 で、全ステップの actions / rewards が完全一致。
さらに主実験 100 trial の summary / curves でも huang2022・izumi2026(n=1) の全行が
旧結果とビット単位で一致（下記）。n=1 では割当が内部ランク降順に進み未割当集合が常に
{1..M'} に保たれるため r == j が恒等的に成立し、修正の影響を受けない。

### 検証 2: 主実験の同一性 — n=1 は完全一致、n>=2 は不一致（原因特定済み）⚠️

再実行結果（`outputs/runs/20260721_fixspec_good_arm_tradeoff_K20_M8_T1M/`）と
旧結果（`outputs/runs/20260525_131250_good_arm_tradeoff_K20_M8_T1M/`）の比較:

- **huang2022 / izumi2026 n=1: summary.csv・curves.csv の全セルが完全一致**（各 100 trial）。
- **izumi2026 n=2..6: 全 100 trial で不一致**。

不一致の原因は乱数消費や決定順序のバグではなく、**FIX-5 の分岐条件 r != j が
主実験でも毎 trial 発動するため**である。根拠:

1. 修正前コード（git HEAD 版）に計測のみを追加した再実行は、保存済み主実験と
   600/600 trial でビット単位一致（cumulative_regret を CSV の 10 進文字列レベルで照合。
   `outputs/runs/20260721_fixspec_.../old_code_instrumentation_stats.json`）。
   つまり再実行環境・ドライバは旧結果を厳密に再現できる。
2. その旧軌跡の上で数えると、r != j は n=2..6 の**全 trial** で発生
   （n あたり延べ 1847〜1864 回 / 100 trial、trial あたり平均 約 18.5 回）。
   サブリーダーが担当チャネルの accept で先に割当てられ、未割当集合が非連続になる
   状況は主実験でも通常運転で起きる。
3. 一方、FIX-5 が実害として防ぐ「j ベース開始位置の mod |K| 衝突」は旧軌跡上で
   **0 回**（全 n・全 trial）。これは fix.tex の
   「衝突は本編の実験構成では発生を確認していない」という記述と整合する。

つまり「主実験では分岐条件が一度も発動していないはず → ビット単位一致するはず」という
作業前提は、FIX-4(a)（救済 0 回）については正しいが、FIX-5 の r != j については
成り立たない。**最終仕様を忠実に実装する限り、n>=2 の主実験結果の変化は不可避**である。

### 検証 5: 分岐の発動回数まとめ

- FIX-5（r != j）: n=1 では全実験で 0 回。n>=2 では**全実験・ほぼ全 trial で発動**
  （例外は steep の n=6 のみ 8/50 trial）。「主実験では 0 回」という想定は不成立。
- FIX-4(a)（救済割当）: **全実験で 0 回**。steep では前提条件（チャネル棄却）自体が
  0 回であることも確認。good arm は top-n の高期待値アームであり top-M に含まれるため、
  「M0 本のアームに明確に劣る」という棄却条件を満たす状況が実験設定上ほぼ生じない。

## 3. 論文側（ajci2026 リポジトリ）への影響

最終仕様の実装で数値が微変するため、論文の数表・図を最終仕様の実験値に
揃えるなら以下の更新が必要（いずれも結論・順位・成功率は不変）:

1. **本編 6 節の表**（累積リグレット列）: n=2..6 を新値に差し替え
   （上記 main の表。n=1 の 2,033,213 と n*=4・約 49% 削減の記述は不変。
   n=4 最小値は 1,029,282 → 1,029,303）。
2. **補足資料 F 表 tab:steep**: リグレット行を
   1,133,070 / 1,486,616 / 2,066,474 / 1,982,755 / 2,185,496 / 2,194,825 に差し替え
   （成功率行 1.00 / 0.70 / 0.00 / 0.00 / 0.00 / 0.00 は不変）。
3. **補足資料 F の図**（regret_vs_n_K10_M4 / K20_M8 / K30_M12 / steep）と
   本編のリグレット曲線図: 新 curves.csv から再生成（n* の位置・結論は不変）。
4. **fix.tex の「実装への注記」**: FIX-4(a)「(a) は未適用である」、
   FIX-5「実装は j ベースの開始位置のままである」の 2 箇所を
   「実装済み」に書き換え。その際、FIX-5 について
   「本編の実験構成では発生を確認していない」のは開始位置の**衝突**であり、
   未割当集合の非連続化（r != j）自体は発生するため、実装反映後の実験値は
   旧値から微小に変化する（成功率・最適 n は不変）ことを付記するのが正確。
